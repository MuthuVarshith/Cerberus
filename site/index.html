Cerberus

Agents write patches. Cerberus decides whether a patch has earned a pull request.

What it does

A coding agent can produce a plausible diff for almost any bug report in seconds. The bottleneck is not writing the patch — it is deciding whether it deserves a reviewer's attention. An agent judging its own work is the weakest possible evidence: it chose the change, it chose which tests to run, and “the test I wrote passes” says nothing about the tests that already existed.

Cerberus never writes the fix. It takes a patch from wherever it came from — a person, a script, a coding agent, a model — runs it against evidence the patch's author does not control, and ends in exactly one state.

ADMITTED REFUSED · code names the gate ERROR · fails closed

The pipeline

Everything after dependency installation runs offline in a container. All outcomes come from JUnit XML — an unreadable result is a refusal, never a pass.

A real run

Measured against an ungated baseline

24 seeded instances over three small libraries, with hidden specification tests as ground truth that the gate never sees. The baseline is measured, not stipulated: admit whenever the reproduction test passes — what an agent that trusts itself does.

MetricCerberusUngated baseline
Patches admitted1120
Admitted but should have been refused4 (36%)13 (65%)
Admitted code failing hidden tests47
Correct fixes admitted7 of 77 of 7
Rejection accuracy12 of 17—

Four of the eleven admissions were wrong. They are plausible-but-wrong patches that fix the reported symptom and pass every visible test, including the reproduction test, while failing hidden tests.

No amount of gate engineering closes that: visible tests define the visible contract. Cerberus removes the mistakes tests can see — regressions, scope creep, weakened tests, reproductions that never reproduced the bug — and cannot remove the ones they cannot. Measuring it was the point; hiding it would make the project worthless.

Security model

Untrusted repository code runs, so the sandbox is the product as much as the gates are.

  • Two phases. Dependency installation runs in a networked container that is committed to an image; everything after runs offline — --network none, all capabilities dropped, no-new-privileges, memory / CPU / PID limits, tmpfs /tmp, in-container kill timeout.
  • Fails closed. No Docker, no daemon, no image → the run ends in ERROR. There is no host fallback.
  • No credentials cross the boundary. The container receives four fixed variables; a test plants a secret in the host environment and asserts it never appears inside. The GitHub token never enters the sandbox, argv, or a remote URL.
  • The host never follows a workspace symlink. A committed link, or one created by code in the container, would otherwise redirect a harness write outside the workspace on Linux and macOS.
  • No process outlives its command, and a container orphaned by a killed process stops and removes itself.
  • Cerberus never merges. It opens draft pull requests, or reports a Check Run.

Not production-ready

  • Four of eleven benchmark admissions were wrong — a limit of test-based verification, not a missing feature.
  • The Docker path has run on Windows only; the symlink and permission defences matter most on Linux, where they are covered by unit tests run inside a container rather than by a Linux host.
  • The GitHub App is written and tested against a fake GitHub API, never installed on a real repository.
  • No real coding agent has been run through the gate yet; the adapter is exercised by a scripted stand-in.
  • 24 author-written instances and three external bugs show the gates behave as designed — not how often they would help on real projects.
  • Repository code runs in the same process as the test runner, so a deliberately malicious repository could forge its own results. Cerberus verifies patches to trusted-but-buggy repositories.
